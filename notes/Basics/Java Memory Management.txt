- For each method, a stack block is created in the memory, and the method's local variables and parameters are stored in that stack block. When the method execution is completed, the stack block is removed from memory, and all the local variables and parameters are also removed.
- When we create an object, the reference variable that holds the object is stored in the stack, while the actual object is stored in the heap memory. The heap memory is used for dynamic memory allocation, and it allows us to create objects at runtime.
- When we create a string, the reference will be stored in stack, while the actual string abj will be stored in heap, in string pool. The string pool is a special area in the heap memory that is used to store string literals. When we create a string literal, it is stored in the string pool, and if we create another string literal with the same value, it will reference the same object in the string pool instead of creating a new object.
- But when we create a string using the new keyword, it will create a new object in the heap memory, even if the string value is the same as an existing string literal in the string pool. This is because the new keyword always creates a new object in memory, regardless of whether an identical object already exists or not.
- The references in stack will be removed in the LIFO (Last In First Out) order, meaning that the most recently created reference will be removed first when the method execution is completed. This is because the stack operates on a last-in-first-out basis, where the most recently added item is the first one to be removed.
- The scope of the methods finishes, when the closing bracket is reached. That is when the stack block for that method is removed from memory, and all the local variables and parameters associated with that method are also removed. This is because the stack block is only allocated for the duration of the method execution, and once the method finishes, the stack block is no longer needed and can be removed from memory.
- The garbage collector is responsible for automatically freeing up memory that is no longer being used by the program. It runs in the background and periodically checks for objects that are no longer referenced by any part of the program. When it finds such objects, it frees up the memory they occupy, allowing it to be reused for new objects. This helps to prevent memory leaks and ensures that the program can continue to run efficiently without running out of memory.
- JVM controls when to run the garbage collector, and it does so based on various factors such as the amount of available memory, the number of objects in memory, and the overall performance of the program. The garbage collector runs automatically in the background, and it can be triggered manually by calling the System.gc() method, although this is not recommended as it may not always result in immediate garbage collection.
- There are two types of references: Strong and weak. Now when we do "ClassName obj = new ClassName", the obj is a strong reference and when the GC gets invoked, it will not remove it, if the reference is still in stack. But there is something called as weak Reference, WeakReference<ClassName> weakRef = new WeakReference<>(new ClassName()). In this case, the weak reference will not prevent the GC from removing the object it references, even if the weak reference itself is still in stack. So when the GC gets invoked, it will remove the object that is being referenced by the weak reference, if there are no strong references to that object.
- There is another type called as Soft Reference, SoftReference<ClassName> softRef = new SoftReference<>(new ClassName()). In this case, the soft reference will allow the GC to remove the object it references, but only if the JVM is running low on memory. If there are still strong references to the object, then the GC will not remove it, even if there are soft references to it. However, if there are no strong references to the object and the JVM is running low on memory, then the GC may choose to remove the object that is being referenced by the soft reference. But if the JVM have sufficient memory, then the GC will not remove the object, even if there are no strong references to it. This allows the soft reference to be used for caching purposes, where we want to keep an object in memory as long as there is enough memory available, but we want to allow it to be removed if memory is running low.
------------------------HEAP--------------------------
- The heap is divided into two patts: Young gen and old gen. The young gen is further divided into three parts: Eden, Survivor 1 and Survivor 2. When we create a new object, it is first allocated in the Eden space of the young gen. If the object survives for a certain period of time, it is moved to one of the survivor spaces. If it continues to survive, it is eventually moved to the old gen. The old gen is where long-lived objects are stored, and it is typically larger than the young gen.
- When GC is invoked, it will use "Mark and Sweep" algo, it first marks the objs that are no longer referred. Then sweep will remove those, and move the remaining referred objs into S1.Like this, the objs will be moved from S1 to S2. Then if we set the obj with age, after that age, the abj will be automatically moved to old gen. The GC will also compact the memory by moving the remaining objects together to free up space for new objects. This helps to reduce fragmentation in the heap and improve memory utilization. This is known as GC's "mar and sweep with compaction".
- there is also something called as "Metaspace", where the class metadata is stored. The metaspace is a separate area of memory that is used to store information about the classes that are loaded by the JVM. This includes information such as the class name, methods, fields, and other metadata that is needed for the JVM to execute the program. The metaspace is typically allocated in native memory, which is outside of the heap and stack memory areas. This allows the JVM to manage the class metadata separately from the objects that are created in the heap and stack memory areas.
-------------------------VERSIONS OF GC--------------------------
- There are different versions of garbage collectors available in Java, each with its own strengths and weaknesses. Some of the most commonly used garbage collectors include:
  - Serial Garbage Collector: This is a simple garbage collector that uses a single thread to perform garbage collection. It is best suited for small applications with low memory requirements. Disadvantage is that it can cause long pause times during garbage collection, which can impact application performance, since the app threds are paused during garbage collection.
  - Parallel Garbage Collector: This garbage collector uses multiple threads to perform garbage collection, which can improve performance for larger applications with high memory requirements. In java8, the parallel garbage collector is the default garbage collector for server-class machines. It is designed to take advantage of multiple CPU cores and can perform garbage collection in parallel across those cores, which can help reduce pause times and improve application responsiveness.
  - Concurrent Mark-Sweep (CMS) Garbage Collector: This garbage collector performs most of its work concurrently with the application threads, which can help reduce pause times and improve application responsiveness.
  - G1 Garbage Collector: This is a low-pause garbage collector that divides the heap into regions and performs garbage collection in parallel across those regions. It is designed to provide predictable pause times and is suitable for large applications with high memory requirements. It also promises compaction of the heap, which helps to reduce fragmentation and improve memory utilization. The G1 garbage collector is the default garbage collector in Java 9 and later versions.
